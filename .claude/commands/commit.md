# Safe Commit Command

You are performing a thorough, verified git commit for a Foundry/Solidity project. Follow every phase in order. **Do not skip any phase.** If any required check fails, stop and report — do not commit.

---

## Phase 1 — Remote Divergence Check

Check if the remote has changes that could cause conflicts:

```bash
git fetch origin 2>&1
```

Then check divergence:

```bash
git status -sb
git log HEAD..origin/$(git rev-parse --abbrev-ref HEAD) --oneline 2>/dev/null | head -10
```

- If remote has commits ahead of local: **warn the user**, show the commits, and ask them to run `git pull` before committing. Stop here.
- If the branch doesn't exist on remote yet (new branch): proceed normally.
- If local is ahead or even: proceed.

---

## Phase 2 — Sensitive File Guard

Run:

```bash
git diff --name-only HEAD 2>/dev/null; git ls-files --others --exclude-standard
```

Scan the list. If any of these are modified or untracked, **warn loudly and refuse to stage them**:
- `.env`, `.env.*` (except `.env.example`)
- Files containing `PRIVATE_KEY`, `SECRET`, `MNEMONIC` in their name
- `*.pem`, `*.key`, `*.p12`

Never stage or commit these files. Inform the user if found.

---

## Phase 3 — File Relevance and Security Audit

Get the full picture of everything that could be committed:

```bash
git status --short
git diff --name-only HEAD 2>/dev/null
git ls-files --others --exclude-standard
```

Also read the current `.gitignore` so you know what is already excluded:

```bash
cat .gitignore 2>/dev/null || echo "(no .gitignore found)"
```

For every modified, staged, or untracked file, evaluate it against both lists below.

### 3A — Security Risk Files (hard block)

These must **never** be committed under any circumstances. If staged, unstage immediately with `git restore --staged <file>`. If untracked, add to `.gitignore`:

| Pattern | Risk |
|---|---|
| `.env`, `.env.local`, `.env.*.local` (not `.env.example`) | Credentials, RPC keys |
| `*.pem`, `*.key`, `*.p12`, `*.pfx` | Cryptographic key material |
| Files with `PRIVATE_KEY`, `MNEMONIC`, `SECRET`, `PASSWORD` in filename | Credentials |
| `broadcast/*/run-latest.json`, `broadcast/**/dry-run/` | Contains deployer private key in Foundry broadcast logs |
| `keystore/`, `wallet.json` | Wallet files |
| Hardcoded private keys in source — scan with: | |

```bash
grep -rn "0x[0-9a-fA-F]\{64\}" --include="*.sol" --include="*.js" --include="*.ts" --include="*.json" . 2>/dev/null | grep -v "node_modules\|\.git\|out\|cache" | head -20
```

If any 64-char hex string looks like a private key (not a known contract address or tx hash), warn the user and stop.

### 3B — Unnecessary / Junk Files (unstage + gitignore)

These files have no business being in the repository. If staged, unstage them with `git restore --staged <file>`. If untracked, add to `.gitignore`. If already tracked in git history, warn the user:

| Pattern | Reason |
|---|---|
| `out/`, `cache/`, `broadcast/` | Foundry build artifacts — regenerated by `forge build` |
| `node_modules/` | NPM dependencies — installed via `npm install` |
| `*.log`, `history.txt`, `submission.txt` | Runtime output / scratch files |
| `store.md`, `explanation.md`, `vulnerability_summary.md` | Ad-hoc notes not part of source |
| `.DS_Store`, `Thumbs.db`, `*.swp`, `*.swo` | OS/editor noise |
| `frontend/dist/`, `frontend/build/` | Frontend build output |
| `*.tmp`, `*.bak`, `*~` | Temp files |
| `forge-cache/`, `.foundry/` | Tool caches |

### 3C — Borderline Files (ask the user)

For any file not clearly in 3A or 3B but that seems non-essential (e.g. one-off docs, large binaries, auto-generated ABIs committed separately from source), pause and ask:

> "Should `<filename>` be committed? It looks like [reason]. If not, I'll unstage it and add it to .gitignore."

Wait for the user's answer before proceeding.

### 3D — Apply .gitignore Additions

After identifying all files that should be excluded, append them to `.gitignore` in one clean block:

```bash
# Read current .gitignore, then write additions cleanly — no duplicates
```

Use the Edit or Write tool to append a clearly labeled section like:

```
# Auto-added by /commit — build artifacts & sensitive files
out/
cache/
broadcast/
.env
*.log
history.txt
submission.txt
.DS_Store
```

Only add entries that are not already present. Then re-stage `.gitignore` itself if it was modified.

### 3E — Final Staged File Review

After all unstaging and .gitignore updates, run:

```bash
git status
git diff --staged --stat
```

Show the user a clean summary table:

```
✅ Will commit:    src/VaultSentinel.sol, test/VaultSentinelTest.t.sol, .gitignore
🚫 Unstaged:       out/, cache/, .env
📝 Gitignored:     Added 4 new entries to .gitignore
```

If nothing meaningful remains staged after cleanup, tell the user and stop — do not create an empty commit.

---

## Phase 4 — Format Check and Auto-fix

Run the formatter check:

```bash
forge fmt --check 2>&1
```

- If it **passes** (exit code 0): proceed.
- If it **fails**: automatically run the formatter to fix it:

```bash
forge fmt 2>&1
```

Then confirm fix worked:

```bash
forge fmt --check 2>&1
```

If it still fails after fixing, **stop and report the error**.

---

## Phase 5 — Build

Run:

```bash
forge build 2>&1
```

- If build **fails**: stop, show the full error output, do not proceed. Ask the user to fix compilation errors first.
- If build **passes**: proceed.

---

## Phase 6 — Full Test Suite

Run all tests:

```bash
forge test -vvv 2>&1
```

- If **any test fails**: stop, show which tests failed with their error output, do not proceed. The commit must never happen with a broken test suite.
- If **all tests pass**: proceed.

---

## Phase 7 — Analyze Changes

Gather everything needed to write an accurate commit message:

```bash
git status
```

```bash
git diff --staged
```

```bash
git diff
```

```bash
git log --oneline -8
```

Analyze the diffs carefully:
- What files changed and why
- What is the nature of the change: new feature, bug fix, refactor, test, docs, config, etc.
- What problem does it solve or what behavior does it change
- Any formatting-only changes (from Phase 3) — note these as "chore: format" if they're the only changes

---

## Phase 8 — Stage Files

Stage all modified tracked files, **excluding** sensitive files identified in Phase 2:

```bash
git add -u
```

If there are relevant **new untracked files** (new contracts, scripts, tests, config) that should logically be part of this commit, stage them individually by name — never use `git add .` blindly. Show the user which new files you are staging and why.

Run `git status` again to confirm what is staged.

---

## Phase 9 — Commit

If `$ARGUMENTS` was provided by the user, use that as the commit message title. Otherwise craft a message from your Phase 6 analysis following these rules:

- **Title line**: `<type>(<scope>): <short imperative description>` — max 72 chars
  - Types: `feat`, `fix`, `refactor`, `test`, `chore`, `docs`, `style`, `security`
  - Scope: the contract or area changed (e.g. `VaultSentinel`, `CuratedVault`, `deploy`, `tests`)
- **Body** (if needed): explain the *why*, not the what. Keep it under 5 lines.
- Always append the co-author trailer.

Create the commit:

```bash
git commit -m "$(cat <<'EOF'
<your title line here>

<optional body if the change is non-obvious>

Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>
EOF
)"
```

---

## Phase 10 — Confirm and Report

Run:

```bash
git log --oneline -3
git status
```

Report back to the user:
- What was committed (title + hash)
- Which files were included
- Test results summary (X tests passed)
- Whether any formatting fixes were auto-applied
- Whether there are remaining unstaged changes to address

---

## Failure Summary Format

If you stop at any phase, report clearly:

```
❌ COMMIT ABORTED — Phase <N>: <Phase Name>
Reason: <what failed>
Fix: <what the user needs to do>
```
